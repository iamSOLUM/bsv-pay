# Decisions

Running log of non-blocking decisions made while building bsv-pay.

## Licensing

- **MIT, confirmed by the owner (2026-06-10)** after weighing source-available and dual-license options. Rationale: for a hot-wallet CLI, trust and adoption are the asset — auditability is a feature, and the monetization path is around the tool (donations, services, hosting) rather than license sales.

## M1 — Scaffold

- **TOML parser**: `smol-toml` (pure TS, maintained, TOML 1.0). The PRD fixes the major stack but not a TOML library; this is the lightest compliant option.
- **Argon2id**: `@noble/hashes` provides a pure-JS argon2id. Chosen over the native `argon2` package so `npm install -g` never needs a compiler toolchain.
- **Default fee rate**: 50 sats/KB with a 1-sat minimum fee. Mainstream BSV miners currently accept well below this; conservative default, user-tunable via `fee_rate_sats_per_kb` in config.toml.
- **State home override**: `BSV_PAY_HOME` env var redirects `~/.bsv-pay/` — needed for tests and harmless for users.
- **Network naming**: internal `Network` type is `'main' | 'test'` matching WhatsOnChain path segments.
- **ESM**: package is ESM-only (`"type": "module"`); Node >= 20 required, which predates the npm-global target anyway.
- **Commander usage errors**: unknown commands/options/missing args exit 2 and emit the standard JSON error shape when `--json` is present.

## M2 — Wallet

- **Derivation path**: BIP-44 with the registered BSV coin type — `m/44'/236'/0'/{0|1}/{index}` (0 = receive, 1 = change). Some BSV wallets use the BTC coin type (0'); importers coming from those wallets will see an empty balance and should re-import into such a wallet instead. Documented trade-off in README later.
- **Argon2id parameters**: OWASP first recommended config (m=19 MiB, t=2, p=1) — ~0.3 s per unlock in pure JS, acceptable for a CLI that unlocks on every spend. Params are stored in the wallet file so they can be raised without breaking existing wallets.
- **BRC-100**: `init --brc100` returns a clear `brc100_not_supported` error (exit 2); `src/wallet/brc100.ts` holds the future interface.
- **Non-interactive `init` (create)**: allowed when `BSV_PAY_PASSPHRASE` is set; the new seed is printed to stderr with a warning and the write-it-down confirmation is skipped, so scripts/CI can provision wallets. Interactive runs must re-type a randomly chosen seed word (3 attempts).
- **Seed display in `--json` mode**: the seed phrase and all prompts go to stderr; the JSON result never contains key material (invariant 4). Scripts that need the seed must capture stderr deliberately.
- **`init --force`**: overwrites the wallet file but keeps the old ledger (history is append-only); stale `address_issued` entries from the previous wallet are ignored because tracked addresses derive from wallet counters, not the ledger.
- **All interactive prompts write to stderr**, keeping `--json` stdout machine-clean even mid-prompt.

## M3 — balance

- **Read-only commands don't need the passphrase**: `balance` and `watch` enumerate addresses from the ledger's `address_issued` entries instead of unlocking the wallet. Spending commands still unlock.
- **Broadcast is never silently retried** (unlike GET requests): a retry after an ambiguous failure could mask a double-send. Ambiguity surfaces as exit 6.

## M4 — send

- **UTXO selection**: largest-first greedy with a fee feedback loop. Minimizes input count (and thus fees) for micropayment-sized wallets; no privacy-motivated randomization in the MVP.
- **Dust threshold 135 sats**: change below this is folded into the fee rather than creating an uneconomical output.
- **Fee estimate**: 10 + 148×inputs + 34×outputs bytes (standard P2PKH sizes), rounded up to ≥1 sat. Verified against a real signed tx (225 bytes vs 226 estimated).
- **`--dry-run` persists nothing**: no ledger entry, no change-address counter bump — repeated dry runs are free of side effects.
- **At/above the spend limit interactively**, the user must re-type the amount in sats (stronger than y/N for irreversible money movement).
- **Exit 6 path**: the ledger records the send with `status: "unknown"` and the txid is printed in both human and JSON output so the user can check the explorer before retrying.

## M5 — request

- **`request --wait --json` emits NDJSON** (a `request_created` object, then `payment_received`): a script must learn the address before anyone can pay it, so a single trailing object would be useless. This mirrors the `watch` NDJSON carve-out in invariant 2.
- **Any payment to the request address counts** as fulfilment (the address is fresh, so the first inbound tx is the payment); a short-pay prints a warning but still exits 0. Strict amount matching would strand honest underpayments.
- **`--wait` timeout exits 4** per the PRD's exit-code table, with error code `request_timeout`.

## M6 — watch

- **First polling cycle baselines silently** — pre-existing funds are not session events. The session total counts only payments that arrive while watching.
- **Rate-limit handling**: any chain failure doubles the poll interval (capped at 8×) and resets after a healthy cycle; the session never crashes.
- **Ledger dedupe**: watch appends a `receive` only if no receive with the same txid+address exists (request `--wait` may already have recorded it).
- **Tracked addresses re-read every cycle**, so a `request` issued in another terminal is picked up mid-session.

## M7 — polish

- **Donation address**: mainnet donations go to the real project address `131CswxfV8Swi8zUSc3XfH9tEJLxzxmpa4` (provided by the owner on 2026-06-10). The testnet entry remains the well-known `mipcBbFg…` placeholder (valid checksum, no key holder) and warns accordingly.
- **E2E testnet script** (`scripts/e2e-testnet.mjs`) is gated behind `BSV_PAY_E2E=1`, drives the CLI exclusively through `--json` + exit codes, and requires one manual faucet payment.
- **Local e2e harness (post-MVP)**: BSV testnet faucets are effectively dead (checked 2026-06-10: witnessonchain is the lone survivor, captcha-gated and unusable for the owner; scrypt.io 526, bitails faucet 502, bitcoincloud NXDOMAIN). `scripts/e2e-local.mjs` runs the full definition-of-done loop by spawning the real CLI against an in-process WhatsOnChain-compatible mock over real HTTP; it runs in CI. `BSV_PAY_API_URL` was added to the provider to support this (and any self-hosted WoC-compatible API). The live-testnet script remains for whenever coins are obtainable.

Re-run in Docker (`docker run -it node:22 npm i -g bsv-pay-0.1.0.tgz`) when available.

## M8 — Core library extraction

- **Subpath export, not a monorepo split**: `bsv-pay/core` ships from the same package (`exports` map + declarations). A monorepo/package split is deferred until there is a second consumer with a divergent release cadence.
- **`CliError` is the library error type**, exported as `BsvPayError`. It already carried the stable exit-code number, a snake_case `errorCode`, and a data bag — inventing a parallel hierarchy would just need a mapping layer back.
- **Core results are camelCase**; the stable snake_case `--json` shapes are mapped at the command edge. The JSON contract is a CLI output format, not a TS API convention.
- **`openWallet()` never prompts and never prints**: passphrase comes from the explicit option or `BSV_PAY_PASSPHRASE`; encrypted wallet with neither is code 7. Unlock warnings are collected on `wallet.warnings` (or routed to `onWarning`); the CLI passes its own prompt/stderr handlers. `CoreWallet` exposes addresses/metadata only — the signing wallet sits behind a non-exported WeakMap registry, so key-capable objects never cross the library boundary (invariant 1).
- **Spend-limit placement (transitional)**: the CLI keeps its interactive pre-unlock check (fail-fast exit 8, see M7) and calls core with `allowAboveLimit: true`; core's `planSend` enforces the same config limit for library callers. Both checks collapse into the single `authorizeSpend()` gate in M9.
- **`awaitPayment` writes the receive ledger entry in core** (was in the request command), so library and future MCP callers ledger identically (invariant 6). The CLI re-throws the timeout with its original message/data so `--json` output is unchanged.
- **`getHistory` is ledger-backed** (newest first, type filter + limit) — no chain scan. Fast, offline, and it carries the local-only memos; MCP `get_history` (M10) will consume it as-is.
- **Wallet creation stays CLI-only**: `init` is interactive-heavy (seed confirmation, passphrase choice); the library covers unlock onwards. Revisit if an embedder actually needs programmatic provisioning.
- **`watch` not extracted**: M10's agent surface needs `awaitPayment`, not a streaming watcher; extracting the watch loop now would be speculative.

## M9 — Policy engine

- **One policy.toml for both networks**, with optional `[network.main]`/`[network.test]` override tables; rules are evaluated against the active network's ledger. Simpler than two files, and testnet can get looser budgets via the override.
- **Hard vs soft per-tx limit**: `per_tx_limit_sats` in policy.toml is a hard cap (amount > limit denies; no flag crosses it). When the file omits it (or doesn't exist), the legacy config `spend_limit_sats` applies with its original confirmable semantics (>= prompts / `--allow-large`) — `allowAboveLimit` in the core API now satisfies *only* that legacy rule. The double enforcement from M8 is gone: the engine is the single decision point; the CLI keeps only the interactive prompting (and its pre-unlock fail-fast exit 8, byte-identical messages).
- **Rule order**: denylist → allowlist → hard per-tx → soft per-tx → session budget → daily budget → rate/min → rate/hour → approval threshold → allow. Deny beats queue (queueing an over-budget payment would be unapprovable noise). Threshold queues at/above (`>=`, conservative reading of the spec's "above").
- **Budget accounting**: daily budget and rate limits are recomputed from ledger `send` entries at every decision — amounts only (fees excluded), `unknown` status counts as spent, future timestamps count as now (all conservative). Rate limits count actual payments, not attempts, so denied/cancelled tries don't burn the quota. Session spend is the only in-memory piece, by definition (process lifetime); the ledger-derived daily cap is the restart-proof backstop.
- **Evaluate vs enforce**: `--dry-run` and `policy test` get identical verdicts through the same engine but persist nothing and consume nothing (M4's "dry runs are side-effect free" extends to policy). Real spend decisions — allow, deny, queue — always ledger with rule + reason (invariant 6). Consequence: a confirmed-then-cancelled interactive send leaves an "allowed but not executed" audit entry, which is correct.
- **The gate is two-sided**: `authorizeSpend()` decides in `planSend` (before any network I/O), and `executeSend` only accepts plans recorded in an engine-private WeakMap for exactly that recipient+amount — consumed on broadcast (one authorization = one broadcast), never granted to hand-built, altered, or dry-run plans. Proven by `test/policy-gate.test.ts`: static choke-point scan (broadcast/signing/fetch allowlisted to specific files), runtime forgery rejections, and a sweep provider that fails any broadcast lacking a matching ledgered allow decision. **M10/M11 must add their entry points (MCP `pay`, `paidFetch`) to that sweep.**
- **Approval secret ≠ wallet passphrase**: stored only as an argon2id hash (same OWASP params as the wallet KDF, timing-safe compare, 0600). `approve`/`reject`/`set-secret` demand a real TTY before any prompt and have no env/flag path at all; changing the secret requires the current one; threshold-without-secret fails closed (queues pile up, nothing approvable). The wallet passphrase is explicitly rejected as an approval secret. Unit tests reach the prompts through an internal function parameter the CLI wiring never passes.
- **Approve re-decides**: approval satisfies only the threshold rule; lists, budgets, and rates are re-checked against the ledger at approval time. A deny leaves the approval pending rather than consuming it.
- **Approvals queue lives in the ledger** (queue decisions minus `approval_resolved` entries) — no second mutable state file; `approvals list` is a fold. Exit 7 for a wrong approval secret (auth-failure family), `tty_required`/`approval_secret_missing` are exit 2.
- **Threat-model line (recorded deliberately)**: the engine governs spends that go through bsv-pay. Write access to `~/.bsv-pay` (policy.toml, the ledger, the secret hash) or arbitrary code with the wallet passphrase defeats any local tool — the wallet itself is forfeit at that point. Defenses in scope: 0600 perms, fail-closed approval flow, audit-grade ledger; the M10 deployment keeps the passphrase away from agents entirely. Ledger hash-chaining for tamper *evidence* was considered and deferred — it detects, doesn't prevent, and M9 is already large.
- **Policy cache**: per process keyed by state dir + network + the config spend limit (the synthesized default depends on it). CLI = per invocation; a long-running MCP server picks up edits only on restart, matching invariant 2's "edit + restart".

## M10 — MCP server

- **MCP SDK**: official `@modelcontextprotocol/sdk` **1.29.0** (`^1.29.0`), stdio transport, `McpServer.registerTool` with zod schemas (zod ^3.25, the SDK's own supported range, deduped). Tools declare `outputSchema` from day one — schemas are additive-only once shipped (invariant 3), and the SDK validates every result against them at runtime without stripping unknown keys, so adding optional fields later stays safe.
- **MCP result envelope**: every tool returns `structuredContent` of `{ok: true, ...}` or `{ok: false, code, error, message, ...data}` — the same stable numbers/snake_case codes as the CLI (`code` mirrors exit codes, `error` mirrors the `--json` error field, engine data fields like `remaining_sats` are flattened in). ALL expected failures (`CliError`s: policy denials, queued approvals, no wallet, insufficient funds) map to `ok:false` RESULTS — `isError` is reserved for unexpected exceptions — so an agent can always parse the outcome and adapt instead of seeing an opaque tool error. snake_case chosen to match the CLI `--json` contract: MCP results are a machine contract, not a TS API.
- **MCP server identity & lifecycle**: server name `bsv-pay`, version mirrors the package (0.1.0). The `mcp` command unlocks the wallet once at startup via `BSV_PAY_PASSPHRASE` or a TTY prompt to stderr (no env + no TTY = refuse to start, exit 7; no wallet = exit 2) and serves until stdin EOF. There is no unlock/lock/export tool, so the connected agent never holds a secret. stdout carries only the MCP protocol; all human output goes to stderr (invariant 5's strictest case).
- **MCP `pay` has no soft-limit escape**: the CLI's interactive confirm / `--allow-large` exists for humans; MCP is unattended by definition, so a payment at/above the legacy `spend_limit_sats` is a plain structured denial (`spend_limit_exceeded`). Only a human raising config/policy changes that. Likewise no `dry_run` argument on `pay` for now — smallest possible spend surface; tool schemas are additive, so it can come later if a real agent needs fee previews.
- **`await_payment` only watches addresses this wallet issued** (`unknown_address` otherwise): it appends a `receive` ledger entry when the payment lands, and ledgering receives for arbitrary foreign addresses would falsify the audit trail. Timeout is capped at 600 s per call (default 120) and returns a retry-safe `request_timeout` result, matching MCP clients' expectations of bounded tool calls.
- **`get_policy_status` exposes the full allow/denylist to the agent** (not just counts): the lists are the human's own configuration, not secrets, and an agent that can see "only these recipients are allowed" plans correctly instead of burning attempts. The approval queue is likewise visible (ids/amounts/memos) — approving it stays human-only.
- **e2e step [9/9] spawns the real `bsv-pay mcp` binary** over stdio (SDK `StdioClientTransport` with the env passphrase, i.e. the exact Claude Code deployment shape) against the mock chain, and replays the checkpoint demo: allowance check → pay → structured over-budget denial (ledgered) → denylist refusal → queue visible to `approvals list` → request/await receive loop → stdout/stderr separation.
- **Concurrent spends are single-flighted in core, not at the MCP edge** (owner requirement, 2026-06-11).

## M11 — HTTP 402 (BRC-105)

- **Simplified BRC-105 profile now; full spec compliance arrives with M12.** Researched before building (2026-06-12): BRC-105 *requires* a BRC-103/104 mutually-authenticated session, BRC-29 output derivation, and an AtomicBEEF transaction envelope. The SDK's `AuthFetch` implements all of it — but against a BRC-100 `WalletInterface` (`createAction`, SPV data), which is exactly the custody model M12 introduces. Likewise `@bsv/payment-express-middleware` (Open BSV License) requires Express, `@bsv/auth-express-middleware` (`req.auth.identityKey`), and a wallet with `internalizeAction` — not adaptable to our local BIP-44 wallet without pulling M12 forward. So M11 ships the BRC-105 *header exchange* (same names, flow, version `1.0`, nonce `derivationPrefix`, `x-bsv-payment` JSON retry envelope) with two documented divergences: payment destination is a fresh server-wallet address advertised via an `x-bsv-payment-address` extension header (instead of BRC-29 derivation — same freshness/unambiguity model as `bsv-pay request`, and the funds are visible/spendable by the server wallet immediately), and `transaction` is raw tx hex (instead of AtomicBEEF). bsv-pay's fetch and serve interoperate; interop with external BRC-105 services is deferred to M12, where the client switches to `AuthFetch` for BRC-100-backed wallets.
- **The buyer broadcasts; the seller verifies against its own chain view.** `paidFetch` pays through core `send()` — the policy gate, single-flight lock, and ledger, identical to every other spend path — then retries with the envelope. The middleware structurally pre-checks the presented hex, then confirms via `awaitPayment` on its provider (which also ledgers the `receive`, invariant 6). Consequence: no new broadcast/sign sites exist; the static choke-point scan's only change is allowlisting `\bfetch(` in `http402/client.ts` (an HTTP client categorically needs HTTP; it still cannot sign or broadcast, and the sweep covers it).
- **`max_price` is a parameter check, not a policy rule**: it caps one fetch regardless of policy headroom, evaluated before the gate, never ledgered (same family as amount validation — what the engine never saw it never decided). A 402 price above the cap throws exit 8 `max_price_exceeded` with both numbers.
- **Exit code 10 = `payment_not_redeemed`** (appended, invariant 3): the payment broadcast and is ledgered, but the server still refused the content. The error carries the txid and amount — the money moved; the human can take it up with the seller. Pre-payment protocol failures (bad version, malformed terms) are exit 4 — the spend never happened.
- **Queued 402 payments don't redeem content**: a 402 spend at/above `approval_threshold_sats` queues like any other (exit 9); approving it later pays the seller, but the original HTTP exchange is gone — re-fetching quotes a fresh price. Documented rather than special-cased: the gate stays uniform across spend paths.
- **`requirePayment` is framework-agnostic**: Express-compatible `(req, res, next)` signature typed structurally against node's http primitives, zero new dependencies. Quotes (prefix → fresh address) are in-memory, single-use, 10-minute TTL — a restarted seller re-quotes, which is correct because prices may change. Budgets are recomputed from ledger `send` entries at decision time, but the entry that consumes them lands only after broadcast — so N simultaneous `send()` calls would all be decided against the same untouched budget and all pass. `core/spend-lock.ts` serializes the whole decide→sign→broadcast→ledger span per state dir + network (a promise chain; a failed spend releases the lock without poisoning it). Placed in core per invariant 2 so the MCP `pay` tool, the 402 client, and library embedders all inherit it; not exported from `bsv-pay/core`. The `planSend`/`executeSend` split remains unlocked across the gap — it exists for interactive human confirmation (holding a lock across a prompt would be a footgun), and a CLI process is one spend per invocation anyway. Proven by `test/spend-concurrency.test.ts`: racing sends against daily/session budgets and rate limits never overshoot, with the full allow/deny audit trail.

## M12 — BRC-100 custody (experimental)

- **The `--experimental-brc100` escape hatch was invoked, deliberately.** The owner's standing instruction allowed it "if the external-wallet protocol fights back" — it does, on the receive side (below) and on full-BRC-105 testability (bottom). `init --experimental-brc100` is the working flag; plain `--brc100` keeps its stable contract (exit 2, `brc100_not_supported`) but the message now points at the experimental flag. When the limitations fall away, `--brc100` graduates into the real flag.
- **Custody backend = a union behind the existing key boundary.** `core/internal.ts`'s WeakMap now holds `{kind:'local', wallet} | {kind:'brc100', wallet}`. The BRC-100 connection handle is key-capable *by proxy* (it can make the external wallet sign), so it gets the exact same treatment as a signing wallet: never exported, never in a result, proven by the key-boundary scan in `test/brc100.test.ts`. The public `CoreWallet` gains only a readonly `backend` field (additive).
- **The policy gate did not move and did not grow a bypass.** `planSend` authorizes before knowing which backend pays; `executeSend` consumes the authorization before branching. The external wallet is reached through exactly one method (`Brc100Wallet.payToAddress`), called from exactly one place (`executeSend`), only after `takeAuthorizedPlan`. The static choke-point scan gained two rules (`createAction|signAction|internalizeAction` only in `wallet/brc100.ts`; `payToAddress` only there + `core/send.ts`) and the sweep gained a cross-checking mock wallet app that refuses any action without a prior ledgered allow decision.
- **The external wallet funds, signs, AND broadcasts** (one `createAction` with `acceptDelayedBroadcast: false`, so failures surface synchronously instead of in a background queue). bsv-pay deliberately does not pick coins, set fees, or see change addresses — that is the app's custody domain. Consequences: `SendPlan` carries an *estimated* fee for display (`external`/`feeEstimated` additive fields); the *exact* fee, size, change, and rawTxHex are decoded from the returned AtomicBEEF; if a wallet returns a txid with an undecodable tx, the result degrades to txid-only rather than losing a broadcast payment (the ledger entry then omits `fee_sats`).
- **Error mapping onto the stable exit-code families**: wallet reports insufficient funds → 3; wallet refused / human declined the app's prompt → 5 `brc100_action_rejected` (nothing spent); wallet created the action but broadcast outcome unclear (WERR_REVIEW_ACTIONS shape) → 6 `brc100_broadcast_unknown`, ledgered `status: "unknown"` and counted against the session budget, mirroring the local ambiguous-broadcast path; wallet app unreachable → 7 `brc100_unreachable` (connection-level failures only — the request never landed, so "nothing was spent" is safe to claim); network mismatch at connect → 2 `brc100_network_mismatch` (invariant 7: a testnet state dir refuses a mainnet wallet app).
- **Receive-side surfaces refuse (`brc100_receive_not_supported`, exit 2)** — `request`, `watch`, `serve`/`requirePayment()` (at construction), and through core the MCP request tools. Reasoning: a payment address issued by bsv-pay would be derived outside the wallet app's tracking, so funds sent to it would be invisible to and unspendable from the app — silently stranding money is strictly worse than refusing. BRC-100's own receive model (BRC-29 remittance + `internalizeAction`) requires the *payer* to cooperate, which arbitrary BIP-21 payers don't. AGENT-PHASE2's "all commands work identically with either backend" is therefore relaxed under the experimental flag, per the standing instruction's documented-limitations clause; the README carries a support matrix.
- **Dry runs never touch the wallet app**: same policy verdicts, fee shown as the estimate (`fee_estimated: true` in `--json`), `txid` empty — there is no txid until the app signs, and asking it to build-then-abort would reserve its UTXOs and pollute its action log. M4's "dry runs are side-effect free" now extends across the custody boundary.
- **Balance under brc100 is the app's `listOutputs` total** (default basket, paginated): one spendable figure in `confirmed_sats`, `addresses: []`, additive `backend: "brc100"` field. The app does not expose per-address detail or a confirmed/unconfirmed split, and inventing one would be fiction. `getHistory` stays ledger-backed and works unchanged (it records what bsv-pay did, which is exactly its job).
- **Connection plumbing**: SDK `HTTPWalletJSON` substrate (the JSON-API every BRC-100 desktop wallet serves), default `http://localhost:3321`, resolution order wallet-file URL → `BSV_PAY_BRC100_URL` → default; originator string `bsv-pay` (shown by the app in its permission prompts). `WalletClient('auto')` was rejected: deterministic beats substrate guessing in a CLI, and Node has no window.CWI/XDM anyway. Tests and embedders inject a `Brc100Interface` via `CoreOptions.brc100`, mirroring the `provider` seam.
- **Full BRC-105 (AuthFetch) is DEFERRED, with eyes open.** M12 was "the moment to revisit": revisited, and not shipped. (a) AuthFetch pays inside its own retry loop via `wallet.createAction`, so honoring invariant 2 requires a policy-gating WalletInterface proxy — a *second* spend door whose recipient is a server identity key, not an address, silently bypassing address-based allow/denylists. (b) The SDK ships only the *client* side of BRC-103/104; there is no server implementation in our dependency set to test a handshake against, so every test would mock a protocol we have never observed working — unverifiable auth code in the most security-sensitive path. (c) `@bsv/auth-express-middleware`/`@bsv/payment-express-middleware` were already evaluated and rejected in M11 (Express dependency, server-side `internalizeAction` wallet). What M12 *did* deliver toward it: the custody prerequisite exists, and a BRC-100-backed bsv-pay now holds a real `WalletInterface` — the AuthFetch leg is a clean future milestone once a testable BRC-104 counterparty exists. The README caveat was narrowed to say exactly this.

## M13 — launch artifacts and publish prep

- **The two-agent demo's buyer is a scripted MCP-only client, not an LLM**: deterministic, CI-cheap, and the README shows the Claude Code swap-in. It can act ONLY through `tool(name, args)` — the same seven tools an agent gets — so the demo can't cheat. The orchestrator asserts every beat (price discovery, 2 allowed buys, denylist stop, budget stop, ledger contents, seller earnings), making it a smoke test as well as pedagogy; it is NOT wired into CI because e2e steps 9–10 already prove the same surfaces — the demo exists to be watched.
- **The prompt-injection beat is staged on purpose**: the dataset the agent pays for instructs it to pay a third address, and the scripted agent obeys naively. The denylist refusal (ledgered) is the thesis made visceral — policy below the agent, because agent judgment is exactly what an injection compromises.
- **Publish naming executes the Phase-1 decision**: package `bsv-pay-cli` (plain `bsv-pay` is squatted on npm), alias package `bsvpay`, binary stays `bsv-pay` — plus a `bsvpay` bin alias from both packages, so either install yields both names. The alias is a 4-line launcher (`import 'bsv-pay-cli/cli'`) pinned to the **exact** same version, via a new `./cli` subpath export (additive). Installing both packages globally collides on bin names — documented in the alias README rather than engineered around. **Publish-day order: `bsv-pay-cli` first, then `packages/bsvpay`** (the alias depends on the published main package).
- **`prepublishOnly` now runs `npm test && npm run build`** — a money CLI should not be publishable from a red tree, and the ~50 s cost is paid only at publish time.
- **`files` gained `docs/` and `CHANGELOG.md`** so the registry page's relative links (the agentic-payments guide, BRC100.md) resolve from the unpacked package, not just GitHub.
- **Pre-publish verification performed (2026-06-12)**: `npm pack` → global install of the tarball into a fresh prefix (the M7 pattern; Docker still unavailable on this machine) → both bin stubs generated, `--version` 0.2.0, `--json` error shape + exit 2 intact from the installed artifact; the alias launcher run against the local tarball shows the identical contract. The MCP server version mirrors the package (0.2.0).
- **Versioning**: 0.2.0 covers M8–M12 as one minor release; CHANGELOG.md is new and back-fills 0.1.0. The CHANGELOG and guide carry the owner-required disclaimer verbatim in spirit: BRC-100 custody is experimental and mock-tested, pending real-app verification, and stays behind `--experimental-brc100` until that pass happens.
